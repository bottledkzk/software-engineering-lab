## 2. 逐项变更说明

### CHG-01｜v1.1｜计分规则：剩余步数奖励公式
- **改动前**：过关时每剩余 1 步 **+200 分**（固定值）。
- **改动后**：每剩余 1 步奖励 `round(0.8 × scoreTarget / moves)` 分（与关卡目标分挂钩）。
- **原因与证据**：在"达成目标即结算"的规则下，结算总分 ≈ 目标分 + 200×剩余步数，而 3 星需 1.6 倍目标分 → 需要剩余步数 ≥ 0.003×目标分，对 27 步关卡等价于"用 5 步打到目标"，实际不可达。模拟玩家实测证实：固定 200 分/步时 3 星几乎不出现；改为挂钩公式后实测 1/2/3 星分布为 41%/41%/18%。
- **影响需求**：FR-06-4、FR-06-5、FR-07-6（新增校准要求）、7.1（新增派生字段）。
- **对设计的影响**：MOD-01 新增常量 `BONUS_RATIO=0.8` 与函数 `bonusPerStepFor()`；MOD-02 `finalScore()` 增加 `bonusPerStep` 参数；DATA-01 新增派生字段 `bonusPerStep`；DEC-09 记录该权衡。
- **验证**：`tests/logic.test.mjs` 断言（步数奖励公式、结算总分）、`tests/calibrate-levels.mjs`（星级分布）。

### CHG-02｜v1.1｜数据设计：`targetColor` 取值约束
- **改动前**：`clear` 型"指定目标颜色编号，且必须 ∈ 颜色池"。
- **改动后**：必须是 **[0, colors) 内的整数**，校验须拦截负数。
- **原因与证据**：实现中发现 JavaScript 负数取模行为（`(-5) % 6 === -5`），使第 3 章前 5 关的 `targetColor` 为负 → 目标色永远无法被消除，关卡不可能完成。原约束表述无法拦截该情况。
- **影响需求**：FR-05 异常处理、7.1 配置校验规则。
- **对设计的影响**：MOD-03 归一化取模 `((index-6) % colors + colors) % colors`；`validateLevel()` 增加非负校验；ERR-09（配置非法处理）；TEST-08 增加回归用例。
- **验证**：断言"所有消除型关卡 targetColor 合法且非负"与"校验函数能拦截负数 targetColor"。

### CHG-03｜v1.1｜配置：第 3 章步数基准
- **改动前**：第 3 章 16 步（±3 → 表述写作"13~27 步"）。
- **改动后**：第 3 章 **18 步**（±3 → 15~21 步）。
- **原因与证据**：原表述存在算术错误（16±3 = 13~19，而非 13~27），且下限 13 步与 FR-05-2"每关 15~30 步"冲突。
- **影响需求**：FR-08-1、FR-05-2、7.1（`moves` 约束）。
- **对设计的影响**：MOD-03 `CHAPTERS` 第 3 章 `baseMoves = 18`；DATA-01 `moves` 约束保持 15~30。
- **验证**：断言"30 关配置全部通过字段校验（步数 15~30）"。

### CHG-04｜v1.1｜可靠性：存档写入失败场景
- **改动前**：写入失败场景写作"隐私模式、配额耗尽"。
- **改动后**：改为"**配额耗尽、存储被禁用等**"（不再把隐私模式列为必然失败）。
- **原因与证据**：Edge 实测（V-10）：InPrivate 无痕窗口可正常写入 3 MB，原表述与实测不符。
- **影响需求**：FR-11-5、NFR-04a 的验证方法。
- **对设计的影响**：ERR-02（写失败）与 ERR-04（存储不可用）分离设计；TEST-06 用例改为"配额超限 + 存储被禁用"注入。
- **验证**：mock 后端注入 `QuotaExceededError` 的断言（AC-23）与 `null` 后端降级断言（AC-24）。

### CHG-05｜v1.1｜假设与约束：localStorage 配额
- **改动前**：AS-10 表述为"约 5 MB 配额"。
- **改动后**："配额有限（**实测 3~5 MB 之间**）、清缓存导致存档丢失"。
- **原因与证据**：Edge 实测：3 MB 写入成功、5 MB 报 `QuotaExceededError`；清除"Cookie 和其他站点数据"后键消失（5 张截图证据）。
- **影响需求**：AS-10、7.2 存档约束。
- **对设计的影响**：DATA-03 体积预算改按实测下限 3 MB 比对（当前预算 ≤50 KB，余量充足）。
- **验证**：V-10 实测记录 + 《01_设计文档》DATA-03 体积预算核算。

### CHG-07｜v1.2｜新增功能需求：FR-20 离线资源缓存
- **改动前**：§2.3 目标 1 与场景 SC-3 声明"完全离线可玩全部 30 关"，但**没有任何功能需求落实**。
- **改动后**：新增 **FR-20 离线资源缓存**（高）：首次成功加载后缓存全部静态资源；断网可打开/刷新并完整游玩；缓存不可用或写入失败时在线可玩并提示；缓存优先、后台更新；音频等非关键资源懒加载。同步新增 NFR-01f 与 AC-33/AC-34/AC-37。
- **原因与证据**：平台评分反馈指出该需求空洞（"目标有、需求无、设计无"）。
- **影响需求**：新增 FR-20；新增 NFR-01f；新增 AC-33/34/37；与 NFR-01a/01e 联动。
- **对设计的影响**：新增 MOD-09（Service Worker 缓存）与 FLOW-01（冷启动与离线流程）；ERR-07（缓存不可用降级）；DEC-06（离线能力选型）；UI-07 增加离线状态提示；DATA-06 增加缓存生命周期。
- **验证**：TEST-06（断网复测、禁用 SW 注入）；AC-33/34/37。

### CHG-08｜v1.2｜业务规则：星级下限
- **改动前**：FR-07-2 仅定义"R ≥ 1.0 → 1 星；R ≥ 1.3 → 2 星；R ≥ 1.6 → 3 星"，且规则 3 只说明"失败结算 → 0 星"。
- **改动后**：明确"**过关（达成目标）即至少 1 星**"；2/3 星仍按 R ≥1.3/1.6。
- **原因与证据**：消除型关卡"刚好达标"时的局内得分可能低于 `scoreTarget`（`scoreTarget` 是星级基准，不必然 ≤ 达标得分），按原规则会出现"达成目标却 0 星"的逻辑空洞；同时新增配置约束"达标时可得的最低结算总分 ≥ scoreTarget"。
- **影响需求**：FR-07-1、FR-07-2、新增 AC-36。
- **对设计的影响**：MOD-02 `starsFor()` 实现下限（未过关→0；过关→≥1）；FLOW-05 星级分支；TEST-01 增加"0 星局数 = 未过关局数"断言（实测贪心 0 星 46 = 未过关 46；休闲 0 星 135 = 未过关 135）。
- **验证**：断言"过关但分数低于基准 → 1 星（过关下限）"与"0 星只出现在未过关局"。

### CHG-09｜v1.2｜业务规则：特殊方块交换的有效性与扣步
- **改动前**：FR-02 仅定义"形成 3 连即有效交换、消耗 1 步；否则弹回"；FR-04 定义了彩虹/组合爆发的**效果**，但未说明这类交换是否有效、是否扣步（AC-10 也只写效果）。
- **改动后**：FR-02 新增规则 4/5——① 彩虹与任意方块交换、② 两个特殊方块相邻交换（组合爆发）**均判定为有效交换并消耗 1 步**；条纹/炸弹与普通方块交换仍需形成 3 连；任何有效交换有且仅消耗 1 步。AC-10 补"步数 −1"，新增 AC-35（彩虹交换扣步）。
- **原因与证据**：平台反馈指出该分支二义（实现与验收都可能各自理解）；实现侧 `findLegalMoves()`/`resolveSwap()` 已按此实现，需回写需求保持一致。
- **影响需求**：FR-02-4、FR-02-5、FR-04-3、AC-10、新增 AC-35。
- **对设计的影响**：MOD-04 合法性判定（双特殊/彩虹无条件合法，条纹/炸弹需成线）；FLOW-02 分支 A/B；UI-03 步数显示。
- **验证**：断言"特定方块交换规则"（实战 3000 局统计特殊方块合成与组合爆发）+ AC-10/AC-35 用例。

### CHG-10｜v1.2｜业务规则：组合爆发范围精确化
- **改动前**："以交换位置为中心清除 3 行 + 3 列（十字形）"。
- **改动后**："以交换位置所在行为中心行（含上下各 1 行，共 3 行）、所在列为中心列（含左右各 1 列，共 3 列），清除这 3 行 3 列的**全部**方块（十字形），按 2 次连锁计分，并消耗 1 步"。
- **原因**：原表述未说明"3 行 3 列"的基准与边界处理，实现可能产生歧义（例如是否只清 3 行与 3 列交叠部分）。
- **影响需求**：FR-04-3。
- **对设计的影响**：MOD-04 `crossBlastCells()` 实现依据（含边界裁剪：中心在边缘时自动少一行/列）。
- **验证**：AC-10 用例（构造中心 3×3 行列表校验清除范围）。

### CHG-11｜v1.2｜界面与数据：重置进度的清空范围

- **改动后**：明确"清空全部存档与两个榜单记录（总星榜、单关榜），恢复初始状态（金币 0、道具各 1、仅 1-1 解锁），**保留昵称与音量设置**"。

- **对设计的影响**：MOD-05 `reset()` + 应用层重置流程；UI-07 二次确认文案明确写出清空范围。

### CHG-12｜v1.2｜数据设计：示例存档重算与多标签页约束
- **改动前**：§7.2 示例存档（`coins: 320`、`items.shuffle: 2`、`unlockedLevelId: "1-3"`）无法由 FR-07/FR-09 规则复算；多标签页行为未定义。

### CHG-13｜v1.2｜可验证性：统一验证口径
- **改动前**：§7.1 写"用自动求解器对每关**抽样**验证可通关性"，§8.1 写"30 关**全部**可通过自动求解器抽样验证"，AC-11 写"自动求解器 + 人工各通一次"——三处口径不一致，且未给出判定阈值与模拟规模。

- **原因**：口径矛盾 + 无法判定通过标准（平台反馈）。

## 4. 未变更声明

以下内容在本次设计阶段**未做任何改动**，与实验一 v1.2 完全一致：

- 选题与产品定位（单机、无广告、无体力、无内购、无账号）；
